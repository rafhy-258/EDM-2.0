# Phase 1A Data Model Design Note: Configuration

**Scope:** Currency and rates; categories and subcategories; EC member pool and EC levels (per nature); recommending authorities; department-head limit (per nature); delegation matrix; policy versioning; maker-checker.
**Specification:** Master Prompt Parts 4.1, 4.2, 4.8, 5, 13, 21, 22, 23.
**Status:** Approved by the product owner on 04-Nov-2026, with the defaults for open questions 1A-1 to 1A-9 (`docs/open-questions.md`, section A). Items 1 to 7 of section A are not yet confirmed and keep their defaults. Migrations follow the order in section 10. Build progress is in section 13.
**Blocked by:** the Part 18 questions in [open-questions.md](../open-questions.md), items 1 to 7 and the Phase 1A items listed in section 12.

---

## 1. Conventions

These follow ADR-0004 and apply to every table below.

- `id uuid` primary key, generated by the application.
- `tenant_id uuid not null` on every row. Every query filters by tenant (enforced by a base repository).
- `created_at`, `created_by`, `updated_at`, `updated_by` as `timestamptz` (UTC) and `uuid`.
- `row_version bigint not null`, incremented on every update, used as the EF concurrency token and the ETag.
- Configuration tables also carry `is_active boolean not null`.
- Soft delete (`deleted_at timestamptz null`, `deleted_by`) only on tables where deletion is allowed (categories, subcategories, EC members, EC levels, recommending authorities, delegation rules, currencies). Deletion is blocked when used (5.0).
- Money `numeric(18,2)`. Rates `numeric(18,4)`. Names `varchar(n)` with n from the specification.
- All names are snake_case.

**Naming note.** Part 13 lists `ec_members` as a shared table and `opex_ec_level_members` / `capex_ec_level_members` per nature. This note follows that: one shared member pool, and per-nature level tables that reference pool rows.

## 2. Shared configuration tables

### 2.1 `currencies`

| Column | Type | Rules |
|---|---|---|
| code | `char(3)` | Uppercase, `CHECK (code ~ '^[A-Z]{3}$')`. Unique among non-deleted rows per tenant. Locked after creation (application rule). |
| name | `varchar(100)` | Required. |
| is_base | `boolean` | True only for PKR. |
| is_active | `boolean` | PKR cannot be deactivated (application and trigger). |

Unique: `(tenant_id, code)` where `deleted_at is null`.
Seed: PKR, name "Pakistani Rupee", `is_base = true`, rate 1, active.

**Open point:** the "Other" currency (Part 18 item 14). Default: no currency named Other is seeded.

### 2.2 `currency_rates`

| Column | Type | Rules |
|---|---|---|
| currency_id | `uuid` FK → currencies | Required. |
| rate | `numeric(18,4)` | `CHECK (rate > 0)`. For PKR the seeded rate is 1. |
| effective_from | `timestamptz` | Required. |
| effective_to | `timestamptz null` | Set when a newer rate becomes active. |
| is_active | `boolean` | Only one active row per currency. |

Indexes: partial unique `(currency_id) WHERE is_active`. Index `(currency_id, effective_from)`.
Rate rows are insert-only except for `is_active` and `effective_to` when superseded. A rate change inserts a new row, deactivates the old one and sets its `effective_to` in one transaction. Requests snapshot `rate`, `rate record id` and `timestamp` (Part 4.1).

**Usage check.** Deletion of a currency is blocked when any request, draft or rate history row uses it. Rate history always exists once a rate has been set, so in practice a currency with any rate history is deactivated, not deleted. Request tables do not exist until Phase 1C. Until then the check goes through an `IUsageChecker` port that returns zero (see section 8).

### 2.3 `categories`

| Column | Type | Rules |
|---|---|---|
| name | `varchar(200)` | Required. Unique among active rows. |
| description | `varchar(500)` | Optional. |
| is_others | `boolean` | Marks the "Others" category (open point 13). |

Unique: `(tenant_id, lower(name))` where `is_active and deleted_at is null`.

### 2.4 `subcategories`

| Column | Type | Rules |
|---|---|---|
| category_id | `uuid` FK → categories | Required. |
| name | `varchar(200)` | Required. Unique among active subcategories of the same category. |
| description | `varchar(500)` | Optional. |
| is_others | `boolean` | Marks the "Others" subcategory. |

Unique: `(category_id, lower(name))` where `is_active and deleted_at is null`.

### 2.5 `ec_members` (shared pool)

| Column | Type | Rules |
|---|---|---|
| user_id | `uuid` FK → users | Required. |
| designation | `varchar(32)` enum | `EC_MEMBER`, `CEO`, `CFO`, `HEAD_ADMIN_GST`. |
| is_active | `boolean` | |

Constraints:
- Unique `(tenant_id, user_id, designation)` across all rows, including inactive. A duplicate attempt returns the message "This member already exists with this designation. Reactivate the existing record instead." (Part 5.3, EDM-CFG-001 family).
- Partial unique `(tenant_id, designation) WHERE is_active AND designation <> 'EC_MEMBER'`. This enforces one active CEO, one active CFO and one active Head of Admin & GST (EDM-CFG-004).

### 2.6 `action_tag_sets`

| Column | Type | Rules |
|---|---|---|
| name | `varchar(100)` | Required. |
| designation | `varchar(32) null` | Default set for a designation (pool level). |
| allowed_actions | `text[]` | Subset of `{APPROVE, REJECT, REVERT, FORWARD}`. `CHECK (allowed_actions <@ ARRAY['APPROVE','REJECT','REVERT','FORWARD'])`. |

Rules enforced in the application: `FORWARD` is never allowed for `EC_MEMBER` or stage assignments other than Phase 1 (Part 4.4). `APPROVE` is required for any assignment that can act. Seeded defaults follow the table in Part 4.4.

Assignment-level overrides reference this table from the EC level member row and from the rule's RA or standalone row.

### 2.7 `recommending_authorities`

| Column | Type | Rules |
|---|---|---|
| title | `varchar(200)` | Letters, numbers and spaces only (`CHECK`-equivalent in application and regex in the validator). Read-only after creation. |
| department_id | `uuid` FK → departments | Required. |
| user_id | `uuid` FK → users | Required. The UI lists only users in the selected department. |
| default_action_tag_set_id | `uuid` FK → action_tag_sets | Default: approve, reject, revert. |
| is_active | `boolean` | |

Unique: `(department_id, user_id)` where `is_active and deleted_at is null`. This is the proposed meaning of "duplicate combinations are rejected" (open point 1A-6).

### 2.8 `settings`

| Column | Type | Rules |
|---|---|---|
| key | `varchar(100)` | Unique per tenant. |
| value | `jsonb` | Typed by a registry in code. |

Used for: `DefaultDeptHeadLimitPkr` (seed 20000), maker-checker switch per module (`maker_checker.<module>`), reference-number pattern, and file limits (later phases).

## 3. OPEX configuration tables

### 3.1 `opex_dept_head_limits`

| Column | Type | Rules |
|---|---|---|
| amount_pkr | `numeric(18,2)` | `CHECK (amount_pkr > 0)` (open questions 1A-1 and 1A-2). |
| description | `varchar(500)` | Optional. |
| effective_from | `timestamptz` | Required. |
| effective_to | `timestamptz null` | |
| is_active | `boolean` | |

Constraint: partial unique `(tenant_id) WHERE is_active`. History kept (every change inserts a row). Status filter and history screens read this table.

### 3.2 `opex_ec_levels`

| Column | Type | Rules |
|---|---|---|
| name | `varchar(100)` | Free label. Unique among active rows of the table (per nature because the table is per nature). |
| min_amount_pkr | `numeric(18,2)` | Lower bound, exclusive. `CHECK (min_amount_pkr >= 0)`. |
| max_amount_pkr | `numeric(18,2)` | Upper bound, inclusive. |
| pkr_range | `numrange` generated stored = `numrange(min_amount_pkr, max_amount_pkr, '(]')` | Used by the exclusion constraint. |
| required_member_count | `int` | `CHECK (required_member_count >= 1 AND required_member_count <= 10)` (open point 1A-5 on the cap). |
| min_approvals | `int` | `CHECK (min_approvals >= 1 AND min_approvals <= required_member_count)`. |
| cfo_required | `boolean` | When true, the level must name a CFO (application). |
| ceo_required | `boolean` | When true, the level must name a CEO (application). |
| is_active | `boolean` | |

Constraints:
- `CHECK (min_amount_pkr < max_amount_pkr)`.
- **Range exclusion:** `EXCLUDE USING gist (tenant_id WITH =, pkr_range WITH &&) WHERE (is_active AND deleted_at IS NULL)`. Needs `btree_gist`. Active levels of one nature cannot overlap. Because the table holds one nature, no nature column is needed.
- Partial unique `(tenant_id, lower(name)) WHERE is_active AND deleted_at IS NULL`.

### 3.3 `opex_ec_level_members`

| Column | Type | Rules |
|---|---|---|
| level_id | `uuid` FK → opex_ec_levels | |
| ec_member_id | `uuid` FK → ec_members | Must be an active pool row (application). |
| action_tag_set_id | `uuid` FK → action_tag_sets, nullable | Overrides the designation default. |

Unique: `(level_id, ec_member_id)`.
Application rule: on create, the number of members equals `required_member_count`, with at most 10 on creation (Part 5.3). On edit, the count must match the required count again. A member who is CFO or CEO can be included as an optional member, as allowed by Part 5.3.

### 3.4 `opex_delegation_rules`

| Column | Type | Rules |
|---|---|---|
| category_id | `uuid` FK → categories | Required. |
| subcategory_id | `uuid` FK → subcategories, nullable | Must belong to `category_id` (application and composite FK). |
| route_type | `varchar(16)` | `EC_LEVELS` or `STANDALONE`. |
| standalone_designation | `varchar(32) null` | `CEO`, `CFO` or `HEAD_ADMIN_GST` when `STANDALONE`, otherwise null. |
| standalone_action_tag_set_id | `uuid null` | Required when `STANDALONE`. |
| is_active | `boolean` | |

Constraints:
- `CHECK ((route_type = 'STANDALONE') = (standalone_designation IS NOT NULL))`.
- `CHECK ((route_type = 'STANDALONE') = (standalone_action_tag_set_id IS NOT NULL))`.
- Partial unique index on the rule key, used for duplicate detection (Part 5.2, EDM-CFG-001):
  `(tenant_id, category_id, coalesce(subcategory_id, '00000000-0000-0000-0000-000000000000')) WHERE is_active AND deleted_at IS NULL`.
- The rule has no nature column, because the table is per nature.

### 3.5 `opex_rule_ec_levels`

| Column | Type | Rules |
|---|---|---|
| rule_id | `uuid` FK → opex_delegation_rules | |
| level_id | `uuid` FK → opex_ec_levels | Same nature by table design. |

Unique `(rule_id, level_id)`. Application: an EC_LEVELS rule has at least one level and at least one RA. A standalone rule has no rows here.

### 3.6 `opex_rule_recommending_authorities`

| Column | Type | Rules |
|---|---|---|
| rule_id | `uuid` FK → opex_delegation_rules | |
| recommending_authority_id | `uuid` FK → recommending_authorities | Must be active on publish. |
| action_tag_set_id | `uuid` FK → action_tag_sets | Per-assignment override. |

Unique `(rule_id, recommending_authority_id)`. Any one RA may act (open point 5). Application: standalone rules have no rows here (open point 3).

## 4. CAPEX configuration tables

The same shape as section 3, with the table prefix `capex_`:
`capex_dept_head_limits`, `capex_ec_levels`, `capex_ec_level_members`, `capex_delegation_rules`, `capex_rule_ec_levels`, `capex_rule_recommending_authorities`.

**Why separate tables.** The specification requires OPEX and CAPEX separation (Part 1.2). Separate tables cost duplicated DDL, but the code is shared through generic services parameterised by nature. The duplicated DDL comes from one migration helper, so the two families cannot drift apart.

`capex_eligible_departments` is part of the Phase 1D work and is not created in 1A.

## 5. Policy and maker-checker

### 5.1 `policy_versions`

| Column | Type | Rules |
|---|---|---|
| version_number | `int` | Per tenant, monotonic, unique `(tenant_id, version_number)`. |
| published_at | `timestamptz` | |
| published_by | `uuid` | |
| change_request_id | `uuid null` FK → config_change_requests | Null for the seeded initial version. |
| snapshot | `jsonb` | Full configuration used to route: rates, limits, levels, members, rules, RAs, tags, settings. |

Insert-only. The application has no update path. A trigger rejects updates and deletes.
Requests reference this table through `policy_version_id` (Phase 1C).

### 5.2 `config_change_requests`

| Column | Type | Rules |
|---|---|---|
| module | `varchar(32)` | e.g. `CURRENCY`, `DELEGATION_RULE`, `EC_LEVEL`, `DEPT_HEAD_LIMIT`. |
| target_type | `varchar(64)` | Entity type. |
| target_id | `uuid null` | Null for a create. |
| action | `varchar(16)` | `CREATE`, `UPDATE`, `ACTIVATE`, `DEACTIVATE`, `DELETE`. |
| status | `varchar(16)` | `PENDING`, `APPROVED`, `REJECTED`, `WITHDRAWN`. |
| maker_user_id | `uuid` | |
| checker_user_id | `uuid null` | |
| base_row_version | `bigint null` | Row version of the target when the maker started. |
| before_json | `jsonb null` | |
| after_json | `jsonb` | Full proposed snapshot, applied on approval (ADR-0010). |
| maker_remarks | `varchar(1000)` | Required. |
| checker_remarks | `varchar(1000) null` | Required on reject. |
| applied_policy_version_id | `uuid null` FK → policy_versions | Set when applied. |
| decided_at | `timestamptz null` | |

Constraints:
- `CHECK (checker_user_id IS NULL OR checker_user_id <> maker_user_id)` (maker ≠ checker).
- Partial unique `(target_type, target_id) WHERE status = 'PENDING'` (one pending change per target, ADR-0010).

When maker-checker is off for a module (setting in `settings`), the write applies immediately and still creates a `policy_versions` row and an audit event.

## 7. Triggers and functions (integrity only)

- Insert-only guard on `policy_versions` and `audit_events` (update and delete rejected).
- PKR guard: `currencies` rows with `is_base = true` cannot be deactivated or deleted (trigger).
- No business logic lives in triggers. The rules (duplicate checks, usage checks, overlap messages) are in the application. The database constraints are the last line of defence and return a constraint name that the application maps to an EDM error code.

Error mapping:

| Constraint | Error code |
|---|---|
| `ex_opex_ec_levels_range` (and the CAPEX equivalent) | EDM-CFG-002 |
| Partial unique on active CEO, CFO, HoA | EDM-CFG-004 |
| Rule-key partial unique | EDM-CFG-001 |
| Dept-head limit partial unique | EDM-CFG-001 |
| Currency code unique | EDM-CFG-001 |

## 8. Usage checks and the deferred request tables

Delete and deactivation checks need to know whether requests use a configuration record. Request tables are created in Phase 1C and later. In 1A the Configuration module defines:

```
interface IConfigurationUsageChecker
  Task<IReadOnlyList<UsageReference>> FindUsagesAsync(ConfigEntityRef entity, CancellationToken ct);
```

Phase 1A registers a stub that returns no usages and is covered by a test named `UsageChecker_is_called_before_delete`. Phase 1C replaces the stub with the Expense-OPEX and Expense-CAPEX implementations. The check reads through each module's application interface and never queries another module's tables (ADR-0001).

Usage in Part 5 terms is shown as "used by 3 delegation rules". Rules count as usages for categories, subcategories, EC levels, members and authorities. Rules are themselves usages for categories and subcategories only.

## 9. Routing-related helper logic that lives in Phase 1A

The coverage view (Part 5.2 step 5) needs the same level-selection logic as the routing engine. Phase 1A defines it as a pure function in the Configuration domain:

- `EcLevelBands`: sort the active levels of a nature, detect overlaps (should never occur because of the constraint) and gaps.
- `CoverageAnalyzer.Analyze(levels, departmentHeadLimit)`: returns bands with the lower bound exclusive and upper bound inclusive, the department-head band (Route B) up to the limit, gap bands (blocked by 4.9), a warning when the lowest level starts above the limit (Part 5.2 validation), and overlap warnings.
- `CoverageAnalyzer.Preview(amountPkr, ...)`: returns which band the amount falls into and the chain.

Phase 1B reuses `EcLevelBands` and the boundary rule inside the routing engine. There is one implementation of the boundary rule, and property tests check that the coverage view and the routing engine agree on every boundary.

## 10. Migration plan (Phase 1A)

Each step is one EF migration, followed by a raw-SQL block for constraints EF cannot express.

1. `M1A-01`: shared config tables: `currencies`, `currency_rates`, `settings`, `action_tag_sets`, plus the seed for PKR and default tag sets.
2. `M1A-02`: `categories`, `subcategories`.
3. `M1A-03`: `ec_members`, `recommending_authorities`.
4. `M1A-04`: OPEX configuration (`opex_dept_head_limits`, `opex_ec_levels`, `opex_ec_level_members`, `opex_delegation_rules`, `opex_rule_ec_levels`, `opex_rule_recommending_authorities`) with `btree_gist` and the exclusion constraint.
5. `M1A-05`: CAPEX configuration, same shape.
6. `M1A-06`: `policy_versions`, `config_change_requests`, the insert-only triggers, and the initial policy version (version 1) seeded for the demonstration tenant.

Rollback: every migration has a `Down`. Down scripts are tested in the integration suite. Seeded data is idempotent.

## 13. Build progress and acceptance checklists

### Slice 1: categories and subcategories (M1A-02, part)

Built in this slice: the `Configuration` module (Domain, Application, Infrastructure, Api), migration `0003_configuration_categories.sql`, the endpoints in section 13.1, and the Categories and Subcategories screens.

**Decisions applied in this slice** (from section 2.3, 2.4 and the Master Prompt 5.1):
- Soft delete only. A category with subcategories, or used by a rule or request, cannot be deleted (EDM-CFG-003). Deactivate instead.
- Names are unique among active, non-deleted rows of the same tenant (categories) or of the same category (subcategories). Comparison ignores case. The message is a field error (EDM-VAL-001).
- Every update carries the row version read earlier. A stale version returns EDM-CONC-001 (412).
- Every create, update and delete writes an audit event with the old and new values (module `Configuration`).
- The usage checker (section 8) is a stub that reports no usages until Phase 1C. Deactivation warnings listing rules therefore show nothing yet.
- A new subcategory needs an active category (the server refuses a missing or inactive one with a field error on `categoryId`).
- `is_others` is in the table but not exposed. The Others routing is open point 13 in section 12.
- Categories are not under maker-checker. Part 5.0 lists only the matrix, EC levels, limits and currency rates.
- Build order. Part 24.3 lists currency first. The product owner asked for configuration screens in the order categories, subcategories, financial limits, approval authorities and policies. This category slice followed that order; currency administration was implemented in a later slice below.
- Policy versions (Part 4.8) are not created yet. They depend on `policy_versions` in M1A-06. This is a known gap, not a choice.

### Slice 2: department-head financial limits (M1A-04, part)

Built in this slice: migration `0005_configuration_dept_head_limits.sql` (tables `opex_dept_head_limits` and `capex_dept_head_limits`, section 3.1, with the same shape for CAPEX), the Limits code in the Configuration module (Domain, Application, Infrastructure, Api), the Financial Limits screen with OPEX and CAPEX tabs, and the tests listed in 13.4.

**Decisions applied in this slice:**
- One PKR limit per nature. OPEX and CAPEX are separate (owner decision on open item 6, the approved default).
- At most one active row per nature and tenant. A unique partial index enforces it. A save closes the active row with `effective_to` set to the new effective date, then inserts the new row. Nothing is deleted.
- Row versions never repeat within one nature. The new open row takes a version above every earlier row, so a client holding an old version cannot match a later row (found by CI; see the verification record).
- The seeded default is `DefaultDeptHeadLimitPkr` = 20,000 (approved 1A-1). It applies while no row is in effect. It is a code constant until the `settings` table exists (section 2.8).
- A saved amount must be greater than zero (1A-2), at most two decimals, below 10^16 (the column limit), and paired with a description of at most 500 characters.
- The effective date is a Karachi (UTC+5) calendar date. It cannot be in the past, and cannot be earlier than the start date of the active row. It is stored as Karachi midnight.
- Status: an open row that has started is **Active**. An open row that starts later is **Scheduled**, and the previous limit (or the default) still applies until then. No open row is **Default**.
- Concurrency: a save sends the `rowVersion` of the open row. No open row means no version is sent. A mismatch returns EDM-CONC-001 (412). So does a race that breaks the unique index.
- Deactivate closes the open row at `max(now, its start)`. The default then applies.
- Every change writes an audit event with the old and new values. A save writes two: `Replaced` (the closed row) and `Created` (the new row). Deactivation writes `Deactivated`.
- Changes apply as soon as they are saved. **Deviation:** the spec (5.0) requires maker-checker for limits, and policy versions (4.8, M1A-06) are not built. The screen says so. This is a known gap, not a choice, and it must be closed before go-live.
